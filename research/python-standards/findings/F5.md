# F5: Security, privacy & logging standards

## Findings

### [1] OWASP Logging Cheat Sheet requires never logging sensitive PII, session IDs, tokens, passwords, connection strings, or encryption keys; those must be removed, masked, sanitized, hashed, or encrypted instead
- quote: "The following should usually not be recorded directly in the logs, but instead should be removed, masked, sanitized, hashed, or encrypted: Application source code; Session identification values...; Access tokens; Sensitive personal data and some forms of personally identifiable information (PII) e.g. health, government identifiers, vulnerable people; Authentication passwords; Database connection strings; Encryption keys and other primary secrets"
- url: https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html
- source_type: primary
- published: unknown (living cheat sheet)
- confidence: high

### [2] OWASP Logging Cheat Sheet names health data, government identifiers, and data about vulnerable people as the highest-sensitivity PII class to exclude from logs
- quote: "Sensitive personal data and some forms of personally identifiable information (PII) e.g. health, government identifiers, vulnerable people"
- url: https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html
- source_type: primary
- published: unknown
- confidence: high

### [3] OWASP recommends structuring every log entry as when/where/who/what (timestamp, app id, user identity, event type+severity) and keeping extended details such as HTTP bodies and stack traces in separate files/tables rather than inline
- quote: "The application logs must record \"when, where, who and what\" for each event. ... Consider separate files/tables for extended event information such as error stack traces or a record of HTTP request and response headers and bodies."
- url: https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html
- source_type: primary
- published: unknown
- confidence: high

### [4] OWASP Logging Cheat Sheet requires sanitizing all event data against log injection (CR/LF/delimiter characters) and treating event data from other trust zones as untrusted
- quote: "Perform input validation on event data from other trust zones to ensure it is in the correct format ... Perform sanitization on all event data to prevent log injection attacks e.g. carriage return (CR), line feed (LF) and delimiter characters (and optionally to remove sensitive data)"
- url: https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html
- source_type: primary
- published: unknown
- confidence: high

### [5] OWASP Logging Vocabulary defines a fixed field schema (ISO 8601 datetime with UTC offset, appid, event, level, description, source_ip, hostname, request_uri/method, region) and standard event names (authn_*, authz_*, sensitive_*, malicious_*, session_*) with an explicit data-privacy note that IP and similar fields are optional PII
- quote: "All dates should be logged in ISO 8601 format WITH UTC offset ... Businesses implementing this logging method should consider value of the fields being logged vs. responsibility as a data steward for the data logged. For example: logging user IP address may be useful for detection and response, but may be considered personally identifiable information"
- url: https://cheatsheetseries.owasp.org/cheatsheets/Logging_Vocabulary_Cheat_Sheet.html
- source_type: primary
- published: unknown (cites IBM Cost of a Data Breach Report 2025)
- confidence: high

### [6] OWASP Logging Vocabulary explicitly warns not to log SQLi payloads, full MCP prompts/tool I/O, or CSP report bodies with query strings — log rule IDs, parameter names, and request identifiers instead to avoid secondary sensitive-data and log-injection risk
- quote: "Logging the payload is dangerous and may result in log injection. Prefer recording a detection rule ID / category and the parameter name over logging the full payload. ... Avoid logging the full prompt/tool I/O. Prefer logging a detection category or rule ID, the target tool/server, and request identifiers ... Strip the query string/fragment before logging"
- url: https://cheatsheetseries.owasp.org/cheatsheets/Logging_Vocabulary_Cheat_Sheet.html
- source_type: primary
- published: unknown
- confidence: high

### [7] Loguru's official security recipe requires diagnose=False in production (default True can leak credentials via exception variable dumps), escaping user-controlled format strings (attribute access can reveal SECRET_KEY), log-injection escaping, and 0o600 file permissions via a custom opener
- quote: "by default, Loguru will display the value of existing variables when an Exception is logged. This is very useful for debugging but could lead to credentials appearing in log files. Make sure to turn it off in production (or set the LOGURU_DIAGNOSE=NO environment variable). ... If user types \"{value.__init__.__globals__[SECRET_KEY]}\" then the secret key is displayed. ... Loguru creates files using the built-in open() function, which means by default they might be read by a different user than the owner."
- url: https://loguru.readthedocs.io/en/stable/resources/recipes.html
- source_type: primary
- published: unknown
- confidence: high

### [8] HIPAA Security Rule (45 CFR 164.312) technical safeguards map directly to code standards: access control, audit controls (record and examine activity in systems containing ePHI), integrity controls, person or entity authentication, and transmission security
- quote: "Access Control. A regulated entity must implement technical policies and procedures for its electronic information systems that maintain ePHI to allow only authorized persons to access ePHI. Audit Controls. A regulated entity must implement hardware, software, and/or procedural mechanisms to record and examine activity in information systems that contain or use ePHI. ... Authentication. ... Transmission Security."
- url: https://www.hhs.gov/hipaa/for-professionals/security/laws-regulations/index.html
- source_type: primary
- published: 2003-02-20 (final rule); page last reviewed 2026-08-07
- confidence: high

### [9] HIPAA Security Rule documentation and written policies/procedures must be retained until six years after creation or last effective date, and regulated entities must regularly review records of activity to track access to ePHI and detect security incidents
- quote: "A regulated entity must implement procedures to regularly review its records to track access to ePHI and detect security incidents ... maintain documentation required for written policies and procedures implemented to comply with the Security Rule and actions, activities, or assessments required by the Security Rule to be documented until six years after the later of: 1) the date of the document's creation or 2) the date the document was last in effect."
- url: https://www.hhs.gov/hipaa/for-professionals/security/laws-regulations/index.html
- source_type: primary
- published: 2003-02-20 / 2013 Omnibus Final Rule; page last reviewed 2026-08-07
- confidence: high

### [10] GDPR Article 25 requires data protection by design and by default: technical and organisational measures such as pseudonymisation to implement data minimisation, and by default only personal data necessary for each specific purpose are processed (amount, extent, storage period, accessibility)
- quote: "implement appropriate technical and organisational measures, such as pseudonymisation, which are designed to implement data-protection principles, such as data minimisation, in an effective manner ... by default, only personal data which are necessary for each specific purpose of the processing are processed. That obligation applies to the amount of personal data collected, the extent of their processing, the period of their storage and their accessibility."
- url: https://gdpr-info.eu/art-25-gdpr/
- source_type: primary
- published: 2016-04-27 (Regulation (EU) 2016/679); applied 2018-05-25
- confidence: high

### [11] OWASP Secrets Management Cheat Sheet requires centralized secrets storage, least-privilege access, automated rotation, never transmitting secrets in plaintext, and auditing who requested/used/rotated each secret; secrets must not live in source code or be leaked via pipeline output
- quote: "you must standardize and centralize the secrets management solution ... engineers should not have access to all secrets in the secrets management system, and the Least Privilege principle should be applied ... Never transmit secrets via plaintext. ... Make sure that pipeline output does not leak secrets"
- url: https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html
- source_type: primary
- published: unknown
- confidence: high

### [12] pip-audit 2.10.1 (PyPA, requires Python ≥3.10) scans environments for known vulnerabilities against the PyPI Advisory Database and OSV, supports CycloneDX SBOM emission, --fix auto-upgrade, --locked lockfile audit, and --require-hashes; exit code 1 on any known vuln cannot be suppressed
- quote: "pip-audit is a tool for scanning Python environments for packages with known vulnerabilities. It uses the Python Packaging Advisory Database ... Support for emitting SBOMs in CycloneDX XML or JSON ... Support for automatically fixing vulnerable dependencies (--fix) ... The current codes are: 0: No known vulnerabilities were detected. 1: One or more known vulnerabilities were found. pip-audit's exit code cannot be suppressed."
- url: https://pypi.org/project/pip-audit/
- source_type: primary
- published: 2026-06-10 (v2.10.1)
- confidence: high

### [13] uv's on-sync malware check (preview, as of 2026-08-05 docs) scans the lockfile against OSV MAL advisories from the OpenSSF malicious-packages database and terminates sync on match; enabled via audit.malware-check=true or UV_MALWARE_CHECK=1; uv also exports uv.lock to CycloneDX 1.5 SBOM
- quote: "While syncing, uv can perform a lightweight scan of your lockfile for known malware by checking it against OSV. OSV references MAL advisories from the OpenSSF's malicious packages database. If a locked dependency matches a malware advisory, the sync will be terminated. To enable malware checks, set audit.malware-check = true in your uv settings or set UV_MALWARE_CHECK=1 in your environment. ... uv export --format cyclonedx1.5"
- url: https://docs.astral.sh/uv/concepts/projects/sync/
- source_type: primary
- published: 2026-08-05
- confidence: high

### [14] Bandit is the PyCQA AST-based Python SAST tool; its plugin set covers hardcoded secrets (B105–B107, B109), bad file permissions (B103), weak crypto (B502–B505), subprocess/shell injection (B602–B608), and ML-specific loads (B614 pytorch_load, B615 huggingface_unsafe_download)
- quote: "Bandit is a tool designed to find common security issues in Python code. To do this, Bandit processes each file, builds an AST from it, and runs appropriate plugins against the AST nodes. ... B105: hardcoded_password_string ... B103: set_bad_file_permissions ... B505: weak_cryptographic_key ... B602: subprocess_popen_with_shell_equals_true ... B614: pytorch_load ... B615: huggingface_unsafe_download"
- url: https://bandit.readthedocs.io/en/latest/ and https://bandit.readthedocs.io/en/latest/plugins/index.html
- source_type: primary
- published: unknown
- confidence: high

### [15] OWASP Vulnerable Dependency Management Cheat Sheet requires automated dependency analysis from project birth, treats risk-acceptance as a CISO/CRO decision, and states that silencing a scanner or bumping a version string is not remediation; when a fix cannot be adopted, isolate and backport the security-relevant change
- quote: "It's highly recommended to perform automated analysis of the dependencies from the birth of the project. ... this decision must be taken by the Chief Risk Officer ... Silencing the scanner or bumping a version string is not remediation. ... Isolate the security-relevant change from the rest of the upstream release."
- url: https://cheatsheetseries.owasp.org/cheatsheets/Vulnerable_Dependency_Management_Cheat_Sheet.html
- source_type: primary
- published: unknown
- confidence: high
