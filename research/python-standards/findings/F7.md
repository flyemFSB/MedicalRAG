# F7: Architecture & package boundary standards

## Findings

### [1] Hexagonal (ports & adapters) architecture exists to keep business logic out of UI/DB layers by exploiting an inside-outside asymmetry, not a left-right stack.
- quote: "The rule to obey is that code pertaining to the inside part should not leak into the outside part."
- url: https://alistair.cockburn.us/hexagonal-architecture/
- source_type: primary
- published: 2005-09-04
- confidence: high

### [2] Cockburn's original paper names the failure mode of layered architecture: teams promise not to put business logic in the new layer, have "no mechanism to detect when a violation of that promise occurs," and a few years later the layer is cluttered again — implying architecture needs an automated check, not just a diagram.
- quote: "However, having no mechanism to detect when a violation of that promise occurs, the organization finds a few years later that the new layer is cluttered with business logic and the old problem has reappeared."
- url: https://alistair.cockburn.us/hexagonal-architecture/
- source_type: primary
- published: 2005-09-04
- confidence: high

### [3] Ports are defined by purposeful conversation, not technology; Cockburn favors a small number of ports (typically two to four) with multiple substitutable adapters per port (GUI, test harness, mock DB, real DB).
- quote: "A port identifies a purposeful conversation. There will typically be multiple adapters for any one port... My selection tends to favor a small number, two, three or four ports."
- url: https://alistair.cockburn.us/hexagonal-architecture/
- source_type: primary
- published: 2005-09-04
- confidence: high

### [4] Ports/adapters split into primary (driving: user, test harness) and secondary (driven: database, external service); primary test doubles are drivers like FIT, secondary test doubles are in-memory mocks.
- quote: "In implementation, ports and adapters show up in two flavors, which I'll call primary and secondary... They could be also called driving adapters and driven adapters."
- url: https://alistair.cockburn.us/hexagonal-architecture/
- source_type: primary
- published: 2005-09-04
- confidence: high

### [5] Martin's Clean Architecture Dependency Rule: source-code dependencies may only point inward; inner circles must not name any entity declared in an outer circle (functions, classes, variables, or data formats generated by outer-layer frameworks).
- quote: "The overriding rule that makes this architecture work is The Dependency Rule. This rule says that source code dependencies can only point inwards. Nothing in an inner circle can know anything at all about something in an outer circle."
- url: https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html
- source_type: primary
- published: 2012-08-13
- confidence: high

### [6] Clean Architecture requires Dependency Inversion at every boundary crossing: the use case calls an interface declared in the inner circle; the outer presenter/adapter implements it, so source-code dependencies oppose the flow of control.
- quote: "So we have the use case call an interface (Shown here as Use Case Output Port) in the inner circle, and have the presenter in the outer circle implement it."
- url: https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html
- source_type: primary
- published: 2012-08-13
- confidence: high

### [7] Clean Architecture forbids leaking framework/ORM types across boundaries: only simple structs/DTOs/args cross; database row structures must not be passed inward because that forces the inner circle to know an outer circle.
- quote: "We don't want to cheat and pass Entities or Database rows... if the database is a SQL database, then all the SQL should be restricted to this layer."
- url: https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html
- source_type: primary
- published: 2012-08-13
- confidence: high

### [8] Import Linter is the production-stable Python tool for machine-enforcing architecture contracts on imports (v2.15, BSD-2-Clause, Python >=3.10, Development Status 5); it supports forbidden, protected, layers, independence, and acyclic_siblings contracts plus custom types.
- quote: "Import Linter allows you to impose constraints on the imports between your Python modules."
- url: https://pypi.org/project/import-linter/
- source_type: primary
- published: 2026-09-04
- confidence: high

### [9] Import Linter `layers` contracts enforce high-to-low dependency direction and include indirect imports, so a lower layer cannot smuggle a dependency on a higher layer through an unlisted intermediate module (e.g. `utils`).
- quote: "This includes indirect imports (i.e. chains of imports via other modules), so if there was a module not listed here that imports high (say, utils) then low wouldn't be allowed to import that either."
- url: https://import-linter.readthedocs.io/en/stable/contract_types/layers/
- source_type: primary
- published: unknown
- confidence: high

### [10] Import Linter `acyclic_siblings` detects sibling dependency cycles that pure module-level cycle checks miss: children of a package may form a cycle (blue→green→red→yellow→blue) even when no individual Python modules form a direct import cycle; drill-down depth defaults to 10 generations.
- quote: "While no direct cycles exist between individual Python modules, an acyclic_siblings contract running on mypackage will detect a cycle between the children of mypackage."
- url: https://import-linter.readthedocs.io/en/stable/contract_types/acyclic_siblings/
- source_type: primary
- published: unknown
- confidence: high

### [11] uv workspaces are the Cargo-inspired monorepo package model: members each have their own `pyproject.toml`, share one lockfile, and are intended to "enforce isolation and separation of concerns" — but uv explicitly cannot stop a member from importing another member's declared dependencies because "Python does not provide dependency isolation."
- quote: "As Python does not provide dependency isolation, uv can't ensure that a package uses its declared dependencies and nothing else. For workspaces specifically, uv can't ensure that packages don't import dependencies declared by another workspace member."
- url: https://docs.astral.sh/uv/concepts/projects/workspaces/
- source_type: primary
- published: 2026-09-15
- confidence: high

### [12] Cosmic Python (Architecture Patterns with Python) frames the cohesion/coupling rule: local coupling is good when elements have high cohesion; global coupling between non-cohesive elements grows superlinearly into Ball of Mud — the cure is a simpler abstraction that hides messy details, not more glue.
- quote: "Locally, coupling is a good thing: it's a sign that our code is working together... Globally, coupling is a nuisance... if we're unable to prevent coupling between elements that have no cohesion, that coupling increases superlinearly until we are no longer able to effectively change our systems."
- url: https://www.cosmicpython.com/book/chapter_03_abstractions.html
- source_type: secondary
- published: 2020
- confidence: high

### [13] Cosmic Python's canonical package layout isolates domain from infrastructure by folder: `src/allocation/{domain,adapters,entrypoints,service_layer}`, with tests split into `unit` / `integration` / `e2e` so test types run separately.
- quote: "All the source code for our app, including the domain model, the Flask app, and infrastructure code, lives in a Python package inside src... domain/, infrastructure/, services/, and api/."
- url: https://www.cosmicpython.com/book/appendix_project_structure.html
- source_type: secondary
- published: 2020
- confidence: high

### [14] Cosmic Python explicitly warns against grab-bag modules: a config module must not become "a dumping ground that is full of things only vaguely related to config and that is then imported all over the place" — keep it immutable and import it from one bootstrap place.
- quote: "Don't let this config module become a dumping ground that is full of things only vaguely related to config and that is then imported all over the place."
- url: https://www.cosmicpython.com/book/appendix_project_structure.html
- source_type: secondary
- published: 2020
- confidence: high

### [15] Fowler (citing Evans 2003) states that "total unification of the domain model for a large system will not be feasible or cost-effective"; DDD therefore divides large systems into Bounded Contexts, each with its own unified model, because polysemes like "Customer"/"Product" break under precision.
- quote: "total unification of the domain model for a large system will not be feasible or cost-effective"
- url: https://martinfowler.com/bliki/BoundedContext.html
- source_type: secondary
- published: 2014-01-15
- confidence: high

### [16] Python's official tutorial confirms packages are dotted-name namespace structuring (`sound.effects.echo`) and recommends `from package import specific_submodule` over star-imports; star-imports are "frowned upon" in production code because they introduce unknown names and shadow submodules.
- quote: "In general the practice of importing * from a module or package is frowned upon, since it often causes poorly readable code."
- url: https://docs.python.org/3/tutorial/modules.html
- source_type: primary
- published: 2026-09-14
- confidence: high
