# F3: Async Python standards

## Findings

### [1] AnyIO uses level-triggered cancellation (Trio model), unlike asyncio's edge cancellation: a task stays cancelled at every yield point until it exits the cancelled cancel scope.
- quote: "Asyncio employs a type of cancellation called _edge cancellation_. ... In contrast, tasks that either explicitly use a cancel scope, or are spawned from an AnyIO task group, use _level cancellation_. This means that as long as a task remains within an _effectively cancelled_ cancel scope, it will get hit with a cancellation exception any time it hits a _yield point_"
- url: https://anyio.readthedocs.io/en/stable/cancellation.html
- source_type: primary
- published: unknown (current stable docs; AnyIO 4.x)
- confidence: high

### [2] AnyIO and Trio require re-raising cancellation exceptions; swallowing them can leave the app in undefined state.
- quote: "Always reraise the cancellation exception if you catch it. Failing to do so may cause undefined behavior in your application."
- url: https://anyio.readthedocs.io/en/stable/cancellation.html
- source_type: primary
- published: unknown
- confidence: high

### [3] Cleanup that awaits inside an already-cancelled scope must be shielded (CancelScope(shield=True) combined with move_on_after/fail_after), otherwise the cleanup await is cancelled immediately.
- quote: "If you need to use `await` during finalization, you need to enclose it in a shielded cancel scope, or the operation will be cancelled immediately since it's in an already cancelled scope"
- url: https://anyio.readthedocs.io/en/stable/cancellation.html
- source_type: primary
- published: unknown
- confidence: high

### [4] Yielding inside a cancel-scope/task-group in an async generator corrupts cancel-scope stack; wrapping that yield in @asynccontextmanager is usually safe only if the same host task runs the whole block.
- quote: "Yielding in an async generator while enclosed in a cancel scope ... # Bad! async def some_generator(): async with create_task_group() as tg: tg.start_soon(foo); yield"
- url: https://anyio.readthedocs.io/en/stable/cancellation.html
- source_type: primary
- published: unknown
- confidence: high

### [5] Trio documents level-triggered cancellation as the fix for the classic production hang where a cleanup await after a timeout would block forever under edge-triggered (asyncio-style) cancellation.
- quote: "if we were using asyncio or another library with “edge-triggered” cancellation, we'd be in trouble: since our timeout already fired, it wouldn't fire again, and at this point our application would lock up forever. But in Trio, this _doesn't_ happen"
- url: https://trio.readthedocs.io/en/stable/reference-core.html
- source_type: primary
- published: unknown
- confidence: high

### [6] asyncio.create_task holds only weak references to Tasks; fire-and-forget tasks without a strong reference can be GC'd mid-execution — keep a set or use asyncio.TaskGroup.
- quote: "Save a reference to the result of this function, to avoid a task disappearing mid-execution. The event loop only keeps weak references to tasks. A task that isn't referenced elsewhere may get garbage collected at any time, even before it's done."
- url: https://docs.python.org/3/library/asyncio-task.html
- source_type: primary
- published: 2026 (Python 3.14.7 docs)
- confidence: high

### [7] asyncio.TaskGroup (3.11+) is the structured-concurrency replacement for bare create_task/gather: on first non-CancelledError failure it cancels siblings and raises ExceptionGroup; gather does not cancel siblings on first exception.
- quote: "The first time any of the tasks belonging to the group fails with an exception other than asyncio.CancelledError, the remaining tasks in the group are cancelled." / "if a task ... raises an exception, TaskGroup will, while gather will not, cancel the remaining scheduled tasks."
- url: https://docs.python.org/3/library/asyncio-task.html
- source_type: primary
- published: 2026 (Python 3.14.7 docs)
- confidence: high

### [8] asyncio.timeout() (3.11+) is the preferred timeout pattern; it converts CancelledError to TimeoutError only outside the async with block — TimeoutError can only be caught outside the CM.
- quote: "The asyncio.timeout() context manager is what transforms the asyncio.CancelledError into a TimeoutError, which means the TimeoutError can only be caught *outside* of the context manager."
- url: https://docs.python.org/3/library/asyncio-task.html
- source_type: primary
- published: 2026 (Python 3.14.7 docs)
- confidence: high

### [9] Swallowing CancelledError breaks TaskGroup/timeout internals; if suppressed, Task.uncancel() must also be called — generally do not suppress.
- quote: "asyncio components that enable structured concurrency, like asyncio.TaskGroup and asyncio.timeout(), are implemented using cancellation internally and might misbehave if a coroutine swallows asyncio.CancelledError. Similarly, user code should not generally call uncancel."
- url: https://docs.python.org/3/library/asyncio-task.html
- source_type: primary
- published: 2026 (Python 3.14.7 docs)
- confidence: high

### [10] A single SQLAlchemy AsyncSession is not safe for concurrent tasks (e.g. asyncio.gather); use a separate AsyncSession per task.
- quote: "The AsyncSession object is a mutable, stateful object which represents a single, stateful database transaction in progress. Using concurrent tasks with asyncio, with APIs such as asyncio.gather() for example, should use a separate AsyncSession per individual task."
- url: https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html
- source_type: primary
- published: unknown (SQLAlchemy 2.0.53 current release 2026-09-14)
- confidence: high

### [11] Under SQLAlchemy asyncio, implicit IO (lazy loading, expired-attribute access) is forbidden; use selectinload/joinedload, AsyncAttrs.awaitable_attrs, or AsyncSession.run_sync().
- quote: "special care must be taken to avoid lazy loading or other expired-attribute access involving ORM relationships and column attributes" / "Accessing the A.bs collection on newly loaded instances of A when eager loading is not in use will normally use lazy loading, which in order to succeed will usually emit IO to the database, which will fail under asyncio as no implicit IO is allowed."
- url: https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html
- source_type: primary
- published: unknown (SQLAlchemy 2.0.53)
- confidence: high

### [12] SQLAlchemy async adapters run sync dialect code via greenlet; the [asyncio] extra installs greenlet so platforms without prebuilt wheels (historically Apple M1) still work.
- quote: "The asyncio extension requires Python 3 only. It also depends upon the greenlet library." / "pip install sqlalchemy[asyncio]"
- url: https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html
- source_type: primary
- published: unknown
- confidence: high

### [13] FastAPI dependencies with yield: code after yield runs after the response by default (scope="request"); Depends(scope="function") closes the dependency after the path operation returns but before the response is sent — critical for DB session/connection ownership.
- quote: "Normally the exit code of dependencies with yield is executed after the response is sent to the client. But if you know that you won't need to use the dependency after returning from the path operation function, you can use Depends(scope=\"function\") to tell FastAPI that it should close the dependency after the path operation function returns, but before the response is sent."
- url: https://fastapi.tiangolo.com/tutorial/dependencies/dependencies-with-yield/
- source_type: primary
- published: unknown (current docs, 2026)
- confidence: high

### [14] FastAPI yield-dependencies: if you catch an exception you must re-raise (or raise HTTPException); otherwise the client still gets 500 but the server logs nothing.
- quote: "If you catch an exception using except in a dependency with yield and you don't raise it again (or raise a new exception), FastAPI won't be able to notice there was an exception" / "the client will see an HTTP 500 Internal Server Error response as it should ... but the server will not have any logs"
- url: https://fastapi.tiangolo.com/tutorial/dependencies/dependencies-with-yield/
- source_type: primary
- published: unknown
- confidence: high

### [15] FastAPI lifespan is a single @asynccontextmanager async generator passed as FastAPI(lifespan=...); on_event("startup"/"shutdown") is deprecated and mutually exclusive with lifespan.
- quote: "The recommended way to handle the startup and shutdown is using the lifespan parameter of the FastAPI app as described above. If you provide a lifespan parameter, startup and shutdown event handlers will no longer be called. It's all lifespan or all events, not both."
- url: https://fastapi.tiangolo.com/advanced/events/
- source_type: primary
- published: unknown
- confidence: high

### [16] FastAPI BackgroundTasks run after the response in the same process; for heavy work or multi-process/multi-server, FastAPI docs point to Celery-style queues (MedicalRAG uses TaskIQ/outbox instead).
- quote: "You can define background tasks to be run after returning a response." / "If you need to perform heavy background computation and you don't necessarily need it to be run by the same process ... you might benefit from using other bigger tools like Celery."
- url: https://fastapi.tiangolo.com/tutorial/background-tasks/
- source_type: primary
- published: unknown
- confidence: high

### [17] Ruff ships flake8-async (ASYNC) rules that encode common production anti-patterns: blocking I/O in async functions (ASYNC210/220/221/222/230/240/250/251), cancel-scope without await (ASYNC100), busy-wait loops (ASYNC110), sleep(0) instead of checkpoint (ASYNC115), yield-in-context-manager-in-async-generator (ASYNC119).
- quote: "ASYNC100 cancel-scope-no-checkpoint ... A with {method_name}(...): context does not contain any await statements." / "ASYNC251 blocking-sleep-in-async-function ... Async functions should not call time.sleep" / "ASYNC230 blocking-open-call-in-async-function"
- url: https://docs.astral.sh/ruff/rules/
- source_type: primary
- published: unknown (current ruff docs, 2026)
- confidence: high
