# F2: Modern Python toolchain standards

## Findings

### [1] Ruff replaces flake8+plugins, Black, and isort in one tool and is 10–100x faster; it ships 900+ built-in rules and is monorepo-friendly via hierarchical cascading config.
- quote: "An extremely fast Python linter and code formatter, written in Rust. … 10-100x faster than existing linters (like Flake8) and formatters (like Black) … Drop-in parity with Flake8, isort, and Black … Over 900 built-in rules … Monorepo-friendly, with hierarchical and cascading configuration"
- url: https://docs.astral.sh/ruff/
- source_type: primary
- published: unknown (live docs; accessed 2026-09-15)
- confidence: high

### [2] Astral officially recommends a curated Ruff rule set — not ALL — starting with E+F and expanding group-by-group; the documented "popular, not too pedantic" example is select = ["E", "F", "UP", "B", "SIM", "I"].
- quote: "Prefer lint.select over lint.extend-select to make your rule set explicit. Use ALL with discretion. Enabling ALL will implicitly enable new rules whenever you upgrade. Start with a small set of rules (select = [\"E\", \"F\"]) and add a group at-a-time. For example, you might consider expanding to select = [\"E\", \"F\", \"B\"] … a configuration that enables some of the most popular rules (without being too pedantic) might look like the following: select = [\"E\", \"F\", \"UP\", \"B\", \"SIM\", \"I\"]"
- url: https://docs.astral.sh/ruff/linter/
- source_type: primary
- published: unknown (live docs; accessed 2026-09-15)
- confidence: high

### [3] Ruff's out-of-the-box default is already a curated high-signal subset (not the full E/W/F plugin universe): defaults include F (Pyflakes), a large UP (pyupgrade) subset, B (bugbear) subset, PL/PLE/PLW correctness rules, RUF, TRY, SIM, PERF, PYI, ASYNC, DTZ, and more — but E501 and most pure-style E rules are off by default (only E722, E902, W605 among E/W).
- quote: "Ruff enables the following rules by default: … \"E722\", \"E902\", \"W605\" … \"F401\" … \"F841\" … \"UP006\" … \"UP007\" … \"B006\" … \"RUF100\" …"
- url: https://docs.astral.sh/ruff/default-rules/
- source_type: primary
- published: unknown (live docs; accessed 2026-09-15)
- confidence: high

### [4] Ruff's formatter is a Black drop-in designed not to innovate on style: on Black-formatted Django and Zulip it emits >99.9% identical lines; config surface is intentionally small (line-length, quote-style, indent-style, docstring-code-format, etc.).
- quote: "the initial goal of the Ruff formatter is not to innovate on code style, but rather, to innovate on performance … When run over extensive Black-formatted projects like Django and Zulip, > 99.9% of lines are formatted identically."
- url: https://docs.astral.sh/ruff/formatter/
- source_type: primary
- published: unknown (live docs; accessed 2026-09-15)
- confidence: high

### [5] Running ruff format requires ignoring formatter-conflicting lint rules (W191, E111, E114, E117, D203, D206, D300, Q000–Q004, COM812, COM819, ISC002 in some setups); none are in Ruff defaults, but enabling parent categories like Q re-introduces them.
- quote: "When using Ruff as a formatter, we recommend avoiding the following lint rules: tab-indentation (W191) … missing-trailing-comma (COM812) … None of the above are included in Ruff's default configuration. However, if you've enabled any of these rules or their parent categories (like Q), we recommend disabling them via the linter's lint.ignore setting."
- url: https://docs.astral.sh/ruff/formatter/
- source_type: primary
- published: unknown (live docs; accessed 2026-09-15)
- confidence: high

### [6] Ruff does not sort imports during format; the official two-step order is `ruff check --select I --fix` then `ruff format` (unified command is planned).
- quote: "Currently, the Ruff formatter does not sort imports. In order to both sort imports and format, call the Ruff linter and then the formatter: ruff check --select I --fix; ruff format"
- url: https://docs.astral.sh/ruff/formatter/
- source_type: primary
- published: unknown (live docs; accessed 2026-09-15)
- confidence: high

### [7] Ruff is not a drop-in replacement for Pylint (~409 rules vs Ruff's 900+, ≥209 overlapping); Pylint does more type inference, and Ruff officially recommends pairing Ruff with a type checker (mypy/pyright/ty) rather than running Ruff alone.
- quote: "At time of writing, Pylint implements ~409 total rules, while Ruff implements over 900, of which at least 209 overlap with the Pylint rule set … Ruff is not a \"pure\" drop-in replacement for Pylint … It's recommended that you use Ruff in conjunction with a type checker, like Mypy, Pyright, or Pyre, with Ruff providing faster feedback on lint violations and the type checker providing more detailed feedback on type errors."
- url: https://docs.astral.sh/ruff/faq/
- source_type: primary
- published: unknown (live docs; accessed 2026-09-15)
- confidence: high

### [8] Production type-checking goal per mypy docs is `mypy --strict`; the documented equivalent config (as of mypy 1.0, still listed in mypy 2.3.1 docs) is warn_unused/redundant_casts/unused_ignores, strict_equality, check_untyped_defs, disallow_subclassing_any, disallow_untyped_decorators, disallow_any_generics, disallow_untyped_calls, disallow_incomplete_defs, disallow_untyped_defs, no_implicit_reexport, warn_return_any, extra_checks — and `strict_optional = false` is explicitly called "evil".
- quote: "An excellent goal to aim for is to have your codebase pass when run against `mypy --strict`. This basically ensures that you will never have a type related error without an explicit circumvention somewhere … strict_optional = false is evil. Avoid using it"
- url: https://mypy.readthedocs.io/en/stable/existing_code.html
- source_type: primary
- published: mypy 2.3.1 docs (accessed 2026-09-15)
- confidence: high

### [9] mypy's official guidance for large codebases: start on a 5k–50k line subset before annotating, pin mypy version with dev requirements, run the same config/file-set for everyone, and gate regressions in CI as soon as possible; introduce strictness per-module once modules are annotated.
- quote: "pick a subset of your codebase (say, 5,000 to 50,000 lines) and get mypy to run successfully only on this subset at first, before adding annotations … Make sure everyone runs mypy with the same version of mypy, for instance by pinning mypy with the rest of your dev requirements … you'll want to make sure to run mypy as part of your Continuous Integration (CI) system as soon as possible."
- url: https://mypy.readthedocs.io/en/stable/existing_code.html
- source_type: primary
- published: mypy 2.3.1 docs (accessed 2026-09-15)
- confidence: high

### [10] uv workspaces are Cargo-style: each member has its own pyproject.toml, the workspace shares a single lockfile; `uv lock` operates on the whole workspace, `uv run`/`uv sync` default to the root and accept `--package`. Members declare each other via `tool.uv.sources = { dep = { workspace = true } }`. Workspaces are unsuitable when members need conflicting requirements or separate venvs; uv enforces a single `requires-python` intersection.
- quote: "a workspace is \"a collection of one or more packages, called workspace members, that are managed together.\" … each package defines its own pyproject.toml, but the workspace shares a single lockfile … Workspaces are not suited for cases in which members have conflicting requirements, or desire a separate virtual environment for each member. … uv's workspaces enforce a single requires-python for the entire workspace, taking the intersection of all members' requires-python values."
- url: https://docs.astral.sh/uv/concepts/projects/workspaces/
- source_type: primary
- published: 2026-09-15 (page date in footer)
- confidence: high

### [11] CI frozen/locked sync is `uv sync --locked` (fail if lockfile is stale) vs `--frozen` (use lockfile without up-to-date check); official GitHub Actions example installs with `uv sync --locked --all-extras --dev` then runs `uv run pytest`, using astral-sh/setup-uv pinned to a specific uv version.
- quote: "To disable automatic locking, use the --locked option: $ uv run --locked ... If the lockfile is not up-to-date, uv will raise an error instead of updating the lockfile. To use the lockfile without checking if it is up-to-date, use the --frozen option … run: uv sync --locked --all-extras --dev … It is considered best practice to pin to a specific uv version"
- url: https://docs.astral.sh/uv/concepts/projects/sync/ (sync flags); https://docs.astral.sh/uv/guides/integration/github/ (CI example)
- source_type: primary
- published: sync page 2026-08-05; GitHub guide 2026-09-15
- confidence: high

### [12] uv.lock is a universal cross-platform lockfile that must be committed; it records exact resolved versions across all markers (OS/arch/Python). `uv lock --check` verifies freshness without rewriting. PEP 751 pylock.toml is an export target, not a replacement for uv.lock inside the project interface.
- quote: "uv.lock is a universal or cross-platform lockfile that captures the packages that would be installed across all possible Python markers … This file should be checked into version control … You can check if the lockfile is up-to-date by passing the --check flag to uv lock … Some of uv's functionality cannot be expressed in the pylock.toml format; as such, uv will continue to use the uv.lock format within the project interface."
- url: https://docs.astral.sh/uv/concepts/projects/layout/
- source_type: primary
- published: 2026-07-21 (page date in footer)
- confidence: high

### [13] PyPA's official packaging guide teaches src-layout (`src/<package>/`): it forces installation before running code, prevents accidental import of the in-development tree (cwd is first on sys.path), and keeps non-importable project files off the editable-install import path.
- quote: "The src layout requires installation of the project to be able to run its code, and the flat layout does not. … The src layout helps prevent accidental usage of the in-development copy of the code. … The src layout helps enforce that an editable installation is only able to import files that were meant to be importable."
- url: https://packaging.python.org/en/latest/discussions/src-layout-vs-flat-layout/
- source_type: primary
- published: unknown (live docs; accessed 2026-09-15)
- confidence: high

### [14] Astral's ty is a production-adjacent Rust type checker claiming 10x–100x faster than mypy and Pyright, with language server, rule levels, per-file overrides, and an official "coming from mypy or pyright" migration guide — relevant as a watch item, not yet a settled default.
- quote: "ty is an extremely fast Python type checker and language server, written in Rust. … 10x - 100x faster than mypy and Pyright … Configurable rule levels, per-file overrides, suppression comments, and first-class project support"
- url: https://docs.astral.sh/ty/
- source_type: primary
- published: 2026-09-15 (page date in footer)
- confidence: medium

### [15] Pre-commit vs CI split per official docs: uv publishes an official pre-commit hook (`astral-sh/uv-pre-commit`, id `uv-lock`) to keep uv.lock in sync locally; mypy docs treat CI as the regression gate (pin version, same invocation for everyone). Local hooks are DX convenience; CI remains the authority.
- quote: "An official pre-commit hook is provided at astral-sh/uv-pre-commit. … To make sure your uv.lock file is up to date even if your pyproject.toml file was changed: … id: uv-lock … you'll want to make sure to run mypy as part of your Continuous Integration (CI) system as soon as possible."
- url: https://docs.astral.sh/uv/guides/integration/pre-commit/ ; https://mypy.readthedocs.io/en/stable/existing_code.html
- source_type: primary
- published: uv pre-commit guide 2026-09-15; mypy docs 2.3.1
- confidence: high
