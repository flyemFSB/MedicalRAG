# F1: Core Python language & typing standards

## Findings

### [1] PEP 484 requires no runtime type checking; annotations are for offline static checkers, and Python remains dynamically typed by design.
- quote: "no type checking happens at runtime. Instead, the proposal assumes the existence of a separate off-line type checker which users can run over their source code voluntarily."
- url: https://peps.python.org/pep-0484/
- source_type: primary
- published: 2014-09-29 (created); Final for Python 3.5
- confidence: high

### [2] PEP 484 recommends annotating all arguments and the return type of checked functions; unannotated slots default to `Any`, and `__init__` ought to be annotated `-> None`.
- quote: "It is recommended but not required that checked functions have annotations for all arguments and the return type. For a checked function, the default annotation for arguments and for the return type is `Any`."
- url: https://peps.python.org/pep-0484/
- source_type: primary
- published: 2014-09-29 (created); Final
- confidence: high

### [3] Python 3.12 typing docs document the canonical type-system spec off-repo at typing.python.org; community tooling (mypy cheat sheet, typing_extensions backports) is the intended companion path.
- quote: "The canonical, up-to-date specification of the Python type system can be found at “Specification for the Python type system”."
- url: https://docs.python.org/3.12/library/typing.html
- source_type: primary
- published: 2023 (3.12 release); docs 3.12.14
- confidence: high

### [4] In Python 3.12, `type Alias = ...` (PEP 695) is preferred over `TypeAlias`; builtin generics and `X | Y` unions replace typing-module aliases, and `Self`/`Never`/`LiteralString` are standard.
- quote: "TypeAlias is deprecated in favor of the `type` statement, which creates instances of TypeAliasType and which natively supports forward references."
- url: https://docs.python.org/3.12/library/typing.html
- source_type: primary
- published: 2023 (3.12)
- confidence: high

### [5] PEP 695 (Python 3.12) introduces `def f[T](...)` / `class C[T]` type-parameter syntax and the `type` statement; variance is inferred from usage, removing the need for most developers to specify covariant/contravariant TypeVars.
- quote: "This PEP eliminates the need for variance to be specified for type parameters. Instead, type checkers will infer the variance of type parameters based on their usage within a class."
- url: https://peps.python.org/pep-0695/
- source_type: primary
- published: 2022-06-15 (created); Final for 3.12
- confidence: high

### [6] PEP 544 defines `typing.Protocol` for structural subtyping (static duck typing); protocols are opt-in for `isinstance` via `@runtime_checkable`, cannot extend regular classes, and should be kept compact rather than large ABC-like interfaces.
- quote: "It is recommended to create compact protocols and combine them."
- url: https://peps.python.org/pep-0544/
- source_type: primary
- published: 2017-03-05 (created); Final for 3.8
- confidence: high

### [7] PEP 544 keeps structural subtyping complementary to nominal subtyping: protocols do not replace ABCs or concrete classes; runtime Protocol objects are simple ABCs with no sophisticated instance checks.
- quote: "we *do not propose* to replace the nominal subtyping described by PEP 484 with structural subtyping completely. Instead, protocol classes as specified in this PEP complement normal classes."
- url: https://peps.python.org/pep-0544/
- source_type: primary
- published: 2017-03-05; Final
- confidence: high

### [8] PEP 589 TypedDict types dicts with a fixed set of string keys; methods are forbidden, runtime type is always plain `dict`, `isinstance` is unsupported, and totality (`total=False`) controls required keys.
- quote: "Methods are not allowed, since the runtime type of a TypedDict object will always be just `dict` (it is never a subclass of `dict`)."
- url: https://peps.python.org/pep-0589/
- source_type: primary
- published: 2019-03-20 (created); Final for 3.8
- confidence: high

### [9] PEP 589 Motivation contrasts TypedDict with dataclasses: dataclasses solve a similar pure-data case but do not directly support JSON serialization, while TypedDict targets JSON-like dict payloads without runtime validation.
- quote: "Dataclasses are a more recent alternative to solve this use case, but there is still a lot of existing code that was written before dataclasses became available... Unlike dictionary objects, dataclasses don't directly support JSON serialization."
- url: https://peps.python.org/pep-0589/
- source_type: primary
- published: 2019-03-20; Final
- confidence: high

### [10] Python 3.12 dataclasses generate `__init__`/`__repr__`/`__eq__` from PEP 526 annotations; `frozen=True` emulates immutability, `slots=True` (3.10+) adds `__slots__`, and unhashable defaults are rejected (use `default_factory` for mutables).
- quote: "by passing `frozen=True` to the `@dataclass` decorator you can emulate immutability."
- url: https://docs.python.org/3.12/library/dataclasses.html
- source_type: primary
- published: 2017 (PEP 557 / 3.7); docs 3.12.14
- confidence: high

### [11] PEP 8 exception norms: derive user exceptions from `Exception` not `BaseException`, design hierarchies by what catchers need, suffix error classes with `Error`, use `raise X from Y` for chaining, and avoid bare `except:`.
- quote: "Derive exceptions from `Exception` rather than `BaseException`. Direct inheritance from `BaseException` is reserved for exceptions where catching them is almost always the wrong thing to do."
- url: https://peps.python.org/pep-0008/
- source_type: primary
- published: 2001-07-05; Active (last modified 2025-04-04)
- confidence: high

### [12] Official 3.12 exceptions docs reinforce hierarchy: all user exceptions should inherit `Exception`; wrong-type args → `TypeError`, wrong-value args → `ValueError`; single inheritance of exception types is recommended; `raise new_exc from original_exc` sets `__cause__`.
- quote: "The built-in exception classes can be subclassed to define new exceptions; programmers are encouraged to derive new exceptions from the Exception class or one of its subclasses, and not from BaseException."
- url: https://docs.python.org/3.12/library/exceptions.html
- source_type: primary
- published: docs 3.12.14; last updated 2026-09-07
- confidence: high

### [13] PEP 257 requires triple-double-quote docstrings; modules, public functions/classes, and public methods (including `__init__`) should have them; function docstrings should cover behavior, args, return, side effects, and exceptions.
- quote: "The docstring for a function or method should summarize its behavior and document its arguments, return value(s), side effects, exceptions raised, and restrictions on when it can be called."
- url: https://peps.python.org/pep-0257/
- source_type: primary
- published: 2001-05-29; Active
- confidence: high

### [14] Google Python Style Guide (production standard) uses a structured docstring format (summary + Args/Returns/Raises/Yields), 80-char lines, strongly encourages type annotations on public APIs, forbids catch-all `except:`, and requires custom exception names end in `Error`.
- quote: "When adding or modifying public APIs, include type annotations and enable checking via pytype in the build system."
- url: https://google.github.io/styleguide/pyguide.html
- source_type: secondary
- published: unknown (living guide; content reflects modern Python with `X | None`)
- confidence: high

### [15] PEP 8 states that function annotations should use PEP 484 syntax (not ad-hoc styles) and that project-specific style guides take precedence over PEP 8 when they conflict.
- quote: "Function annotations should use PEP 484 syntax (there are some formatting recommendations for annotations in the previous section)."
- url: https://peps.python.org/pep-0008/
- source_type: primary
- published: Active
- confidence: high

### [16] PEP 8 baseline layout: 4-space indent; max line length 79 (teams may agree up to 99); docs/comments wrap at 72; spaces preferred over tabs; two blank lines around top-level defs.
- quote: "Limit all lines to a maximum of 79 characters. For flowing long blocks of text with fewer structural restrictions (docstrings or comments), the line length should be limited to 72 characters."
- url: https://peps.python.org/pep-0008/
- source_type: primary
- published: Active
- confidence: high
