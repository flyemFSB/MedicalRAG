# F6: Testing standards & quality gates

## Findings

### [1] The practical test pyramid keeps many small/fast unit tests, some coarse-grained integration tests, and very few end-to-end tests; layer names matter less than consistent granularity and shape.
- quote: "Write tests with different granularity. The more high-level you get the fewer tests you should have... Stick to the pyramid shape to come up with a healthy, fast and maintainable test suite: Write lots of small and fast unit tests. Write some more coarse-grained tests and very few high-level tests"
- url: https://martinfowler.com/articles/practical-test-pyramid.html
- source_type: secondary
- published: 2018-02-26
- confidence: high

### [2] Narrow integration tests should hit one boundary at a time (real local DB/filesystem or a faithful test double), not blast production; broad network integration tests are slower and harder.
- quote: "When writing narrow integration tests you should aim to run your external dependencies locally... Avoid integrating with the real production system in your automated tests."
- url: https://martinfowler.com/articles/practical-test-pyramid.html
- source_type: secondary
- published: 2018-02-26
- confidence: high

### [3] Consumer-driven contract tests (CDC) let consumers publish expectations that providers run continuously, replacing brittle full-stack integration for multi-team interfaces; Pact is the standard tool.
- quote: "Consumer-Driven Contract tests (CDC tests) let the consumers drive the implementation of a contract... The providing team should fetch and run these CDC tests continuously (in their build pipeline) to spot any breaking changes immediately."
- url: https://martinfowler.com/articles/practical-test-pyramid.html
- source_type: secondary
- published: 2018-02-26
- confidence: high

### [4] Pact defines contract testing as checking each application in isolation against a shared contract; unlike a static OAS schema, a Pact contract is "contract by example" enforced by executing concrete request/response cases.
- quote: "Contract testing is a technique for testing an integration point by checking each application in isolation to ensure the messages it sends or receives conform to a shared understanding that is documented in a 'contract'."
- url: https://docs.pact.io/
- source_type: primary
- published: 2026-08-25
- confidence: high

### [5] Standalone provider-side OpenAPI/schema checking does not prove consumers call the provider correctly; Pact docs call integration contract testing more effective at preventing integration bugs.
- quote: "On its own, however, it does not provide any test based assurance that the consumers are calling the provider in the correct manner... and hence, it is not as effective in preventing integration bugs."
- url: https://docs.pact.io/
- source_type: primary
- published: 2026-08-25
- confidence: high

### [6] coverage.py branch coverage tracks line-to-line transitions; a file can be 100% statement-covered while still having partial branches (e.g. `if` never taken false).
- quote: "Where a line in your program could jump to more than one next line, coverage.py tracks which of those destinations are actually visited, and flags lines that haven't visited all of their possible destinations."
- url: https://coverage.readthedocs.io/en/latest/branch.html
- source_type: primary
- published: unknown
- confidence: high

### [7] coverage.py `[report] fail_under` is the official total-coverage gate: if total coverage is under the float target, `coverage report` exits with status code 2.
- quote: "A target coverage percentage. If the total coverage measurement is under this value, then exit with a status code of 2."
- url: https://coverage.readthedocs.io/en/latest/config.html
- source_type: primary
- published: unknown
- confidence: high

### [8] Branch coverage is opt-in via `[run] branch = true` (default False); when enabled, percentage is executions / execution opportunities, counting each line and each branch destination.
- quote: "(boolean, default False) Whether to measure branch coverage in addition to statement coverage... The coverage percentage for a file is the actual executions divided by the execution opportunities. Each line in the file is an execution opportunity, as is each branch destination."
- url: https://coverage.readthedocs.io/en/latest/config.html
- source_type: primary
- published: unknown
- confidence: high

### [9] diff-cover measures patch (diff) coverage as the percentage of new/modified lines covered, and supports `--fail-under` to make incomplete diffs fail CI; it compares Cobertura/LCOV XML against `git diff` vs origin/main.
- quote: "Diff coverage is the percentage of new or modified lines that are covered by tests. This provides a clear and achievable standard for code review: If you touch a line of code, that line should be covered."
- url: https://pypi.org/project/diff-cover/
- source_type: primary
- published: 2026-08-16
- confidence: high

### [10] pytest fixture isolation: fixtures are re-executed per test by default (function scope), return values are cached per test, and yield fixtures with one state-changing action each are the recommended safe teardown structure.
- quote: "The safest and simplest fixture structure requires limiting fixtures to only making one state-changing action each, and then bundling them together with their teardown code"
- url: https://docs.pytest.org/en/stable/how-to/fixtures.html
- source_type: primary
- published: unknown
- confidence: high

### [11] pytest fixture scopes are function (default) / class / module / package / session; session/module scopes share expensive resources (network, containers) but risk cross-test state unless teardown is correct.
- quote: "Possible values for scope are: function, class, module, package or session... the returned fixture value will be shared for all tests requesting it"
- url: https://docs.pytest.org/en/stable/how-to/fixtures.html
- source_type: primary
- published: unknown
- confidence: high

### [12] pytest 9.0 adds a global `strict = true` config enabling strict_config, strict_markers, strict_parametrization_ids, and strict_xfail; docs recommend enabling it on new projects (especially with pinned pytest).
- quote: "Pytest contains a set of configuration options that make it more strict... You can enable all of the strictness options at once by setting the strict configuration option"
- url: https://docs.pytest.org/en/stable/explanation/goodpractices.html
- source_type: primary
- published: unknown
- confidence: high

### [13] pytest recommends src-layout + `--import-mode=importlib` for new projects so tests run against the installed package and avoid sys.path pitfalls of prepend mode.
- quote: "For new projects, we recommend to use importlib import mode... Generally, but especially if you use the default import mode prepend, it is strongly suggested to use a src layout."
- url: https://docs.pytest.org/en/stable/explanation/goodpractices.html
- source_type: primary
- published: unknown
- confidence: high

### [14] pytest-asyncio is the standard plugin for asyncio tests: mark tests with `@pytest.mark.asyncio` and `await` inside; unittest.TestCase subclasses are not supported (use IsolatedAsyncioTestCase instead).
- quote: "@pytest.mark.asyncio\nasync def test_some_asyncio_code():\n    res = await library.do_something()"
- url: https://pytest-asyncio.readthedocs.io/en/stable/index.html
- source_type: primary
- published: unknown
- confidence: high

### [15] Hypothesis is Python's property-based testing library: write tests valid for all inputs in a described range and let Hypothesis generate edge cases you might not think of.
- quote: "Hypothesis is the property-based testing library for Python. With Hypothesis, you write tests which should pass for all inputs in whatever range you describe, and let Hypothesis randomly choose which of those inputs to check - including edge cases you might not have thought about."
- url: https://hypothesis.readthedocs.io/en/latest/
- source_type: primary
- published: unknown
- confidence: high

### [16] mutmut is the production-oriented Python mutation tester (mutmut 3+): it finds surviving mutants, maps them to tests, and can optionally mutate only coverage.py-covered lines; requires fork support (POSIX/WSL).
- quote: "Mutmut is a mutation testing system for Python, with a strong focus on ease of use... Mutmut must be run on a system with fork support. This means that if you want to run on windows, you must run inside WSL."
- url: https://mutmut.readthedocs.io/en/latest/
- source_type: primary
- published: unknown
- confidence: high

### [17] mutmut mutations are intentionally subtle (integer +1, `<` → `<=`, `break` ↔ `continue`); workflow is run → browse → write a killing test → retest, which is how mutation score improves suites.
- quote: "In general the idea is that the mutations should be as subtle as possible... Find a mutant you want to work on and write a test to try to kill it."
- url: https://mutmut.readthedocs.io/en/latest/
- source_type: primary
- published: unknown
- confidence: high

### [18] pytest detects CI via the `CI` or `BUILD_NUMBER` env vars and currently only changes summary truncation; pipeline policy (what runs when) is entirely the project's responsibility.
- quote: "Pytest knows it is in a CI environment when either one of these environment variables is set to a non-empty value: CI... BUILD_NUMBER... For now, the effects on pytest of being in a CI environment are limited."
- url: https://docs.pytest.org/en/stable/explanation/ci.html
- source_type: primary
- published: unknown
- confidence: high
