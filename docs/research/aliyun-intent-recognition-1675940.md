# 阿里云文章 1675940：意图识别方案调研

## 来源

- 文章：[AI 智能体实战：100+次迭代后的意图识别提升之道](https://developer.aliyun.com/article/1675940)
- 页面标题：AI智能体意图识别与槽位抽取的实战演进方案
- 发布日期：2025-08-07
- 调研日期：2026-07-26

本文是阿里云开发者社区作者文章，不是阿里云产品官方规范。文章中的准确率、延迟和成本数据应作为工程方向性参考，不能直接视为 MedicalRAG 的验收指标。

## 文章的核心判断

文章将意图识别和槽位抽取视为 NLU 的两个核心环节，并比较了四种逐步演进的方案：

1. 单节点提示词工程；
2. 意图识别节点与槽位抽取节点分离；
3. 在意图识别前增加意图知识库 RAG 召回；
4. 将意图和槽位重新合并，同时用历史会话 + Case RAG 进行前置增强。

作者最终推荐的高阶方案不是单纯把意图名称做向量分类，而是维护一个可运营的意图 Case 库，在运行时召回与当前问题最相似的案例，将案例改写为提示词上下文，再由 LLM 进行受约束的意图和槽位判断。

## 四种方案

### 方案 A：单节点 Prompt 工程

一个 LLM 节点同时完成意图识别和槽位抽取。提示词包含意图/槽位定义、Few-Shot、CoT 和 JSON/XML 输出格式。

优点是开发成本低、结构简单；缺点是意图增多后提示词膨胀，模型容易受到无关意图和槽位的干扰，线上 Bad Case 通常需要修改提示词并重新发布。

### 方案 B：意图识别与槽位抽取节点分离

先调用意图识别 LLM，再针对每个命中的意图调用独立槽位抽取 LLM。

优点是每个槽位节点职责单一、提示词更短、维护清晰；缺点是调用次数增加，延迟上升。适合意图分支很多且对延迟不敏感的场景。

### 方案 C：前置意图 Case RAG

在意图识别 LLM 前增加意图知识库召回。知识库维护意图描述和大量同义 Query，运行时召回相似 Query 作为 Few-Shot 上下文。

文章建议每个意图准备约 30～50 条种子语料，再用 LLM 生成口语化、命令式、疑问式、描述式等变体。线上出现未覆盖 Query 时，可通过添加知识库条目修复，无需重新修改和发布 Agent。

方案 C 提升了垂类和特殊表达的泛化，但原文明确指出：只针对当前 Query 的召回在多轮对话中效果不足。

### 方案 D：历史会话 + Case RAG + 联合意图槽位处理

方案 D 的关键机制为：

- 维护包含历史提问、最新提问、处理方式、意图和槽位的 Case；
- 将相关历史用户发言与最新 Query 组合后召回；
- 用召回 Case 重写 Prompt，再由一个 LLM 联合完成意图和槽位处理；
- 对已完成的旧意图执行意图切断，避免旧话题污染新意图；
- 对可以用固定 FAQ 直接回答的分支绕过 LLM，以降低延迟。

文章的“思考过程”字段不应原样用于 MedicalRAG。医疗系统应改为可审计的结构化证据字段或简短决策依据，不保存或要求模型输出隐藏 CoT。

## 文章给出的对比数据

测试对象是上海地铁智能体，13 个预设意图，443 条测评用例。原文表格数据如下：

| 指标 | 方案 A | 方案 B | 方案 C | 方案 D |
|---|---:|---:|---:|---:|
| Prompt 长度 | 11000+ 字符 | 意图 1500 + 抽槽 2500 字符 | 意图 1500 + 抽槽 2500 字符 | 5000 字符 |
| 意图/抽槽处理耗时 | 3.18 s | 2.66 s + 2.15 s | 召回 0.24 s + 意图 2.11 s + 抽槽 2.07 s | 召回 0.28 s + 模型 2.43 s |
| 召回/识别准确性 | 92% | 92% | 94.8% | 97.6% |
| Bad Case 修复能力 | 慢 | 慢 | 中 | 快 |
| 开发成本 | 低 | 低 | 中 | 高 |

这些数据没有公开数据集划分、置信区间、准确率定义或线上流量分布，因此只能证明文章作者在其场景中观察到的趋势：Case RAG 和历史上下文管理同时使用时，准确率、可修复性和提示词长度之间的综合平衡最好。

## 对 MedicalRAG 的结论

MedicalRAG 应以 Ragent 的动态意图树为主，并吸收文章 D 的 Case RAG 和历史会话管理：

1. 使用 PostgreSQL + Redis 维护 Ragent 风格的版本化动态意图树，只有叶子节点参与分类；
2. 用 Milvus 建立独立的意图 Case 集合，使用外部 Embedding API 召回，再使用外部 Reranker API 重排；
3. 只把重排后的少量候选意图交给外部 LLM，禁止 LLM 创造新意图、修改安全等级或越过目录白名单；
4. 由受约束的结构化 LLM 调用完成意图和意图专属槽位抽取；只有在歧义或复杂槽位场景下才退化为方案 B 的分离调用；
5. 使用校准后的置信度和拒答/澄清状态，而不是直接相信 LLM 自报的 score；
6. 对多轮会话只保留与当前活动意图相关的结构化上下文，意图完成或话题切换后执行切断；
7. 高风险个体化医疗请求和急症请求在知识库检索前进入安全路径，不能由相似 Case 把它误路由为普通科普问题。

## 与 Ragent 的结合

应复刻 Ragent 的动态意图树、叶子节点分类、系统/知识库/工具路由、Redis 缓存、未知/歧义处理、意图引导、历史会话管理和流式事件顺序。文章 D 的 Case RAG 作为 Ragent 意图树的增强层，而不是替换 Ragent 的目录和路由契约。

### 医疗安全

文章中的“直接回答”只适合系统帮助、固定说明或已审核的非个体化 FAQ。医疗内容仍必须绑定可信证据、风险等级和固定免责声明：

> **AI生成内容仅供参考，不可替代医嘱，请以医生诊断为准**

## 推荐运行时链路

```text
输入归一化/多问题拆分
        ↓
安全规则与话题边界判断
        ↓
Ragent 动态意图树加载与叶子节点筛选
        ↓
Milvus 意图 Case 召回
        ↓
外部 Reranker 重排
        ↓
候选集约束的外部 LLM 意图+槽位判断
        ↓
置信度校准、未知/歧义澄清、意图切断
        ↓
知识库检索 / 安全回复 / 系统回复 / 澄清
```

## 研究建议

上线前应使用 MedicalRAG 自有数据重新评估，至少覆盖普通科普、实体缺失、同义改写、口语/错别字、多轮补槽、多意图、话题切换、急症和个体化用药请求。核心指标应包括 Macro-F1、未知意图召回率、槽位 F1、实体 F1、意图边界 F1、安全误放率、ECE/Brier 校准、P50/P95 延迟、外部 API 调用次数和成本。
