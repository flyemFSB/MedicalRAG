# Qdrant is the unified Hybrid Retrieval engine

MedicalRAG uses a single Qdrant service as the only retrieval engine, replacing the previously selected Milvus standalone and its MinIO/etcd dependencies. Each indexed Chunk stores the versioned dense representation produced by the external Embedding Provider and a precomputed sparse/BM25 representation generated by fastembed's static `Qdrant/bm25` model at index time. A Hybrid Retrieval request runs dense and sparse candidate searches through Qdrant's prefetch API and combines them with Qdrant's built-in Reciprocal Rank Fusion (RRF, k=60); the bounded result set then passes through the application Evidence Fusion stage and the external Reranker API. PostgreSQL remains authoritative for permissions, publication state, provenance, exact filters, and structured medical metadata; it is not a full-text retrieval substitute.

## Rationale

- **Operational simplicity**: Milvus Standalone requires an embedded etcd and an object-storage backend (MinIO) plus Milvus's own metadata service. Qdrant is a single container with no external metadata dependency; Compose drops MinIO and etcd from the core topology ([version-baseline](version-baseline.md) §2). This also removes the MinIO maintenance concern documented in ADR 0017 (community edition unmaintained) for the retrieval path.
- **Native hybrid retrieval**: Qdrant natively supports dense + sparse hybrid search with prefetch requests and a server-side RRF ranker, matching the Ragent-style dense plus BM25 requirement without a second search platform (ADR 0012/0039).
- **Symmetric sparse vectors**: fastembed's `SparseTextEmbedding("Qdrant/bm25")` is a static, corpus-independent model, so index-time and query-time sparse vectors stay symmetric with no stateful BM25 analyzer (official Qdrant recommendation for managed sparse vectors).

## Consequences

- Docker Compose provisions Qdrant but no Milvus, Elasticsearch, pgvector, Neo4j, LightRAG, or other retrieval database; MinIO and etcd are removed from the core service topology.
- Qdrant collection schema and vector configuration must version the dense model, dimension, metric, sparse model, text policy, and fusion policy. A schema or ranking change creates a new collection (index version) rather than mutating the active one in place; collection names carry the immutable Embedding Schema Version.
- The ingestion pipeline writes both dense and sparse vectors before a Published Version becomes retrieval-eligible; points carry payload metadata (`workspace_id`, `is_eligible`, `document_id`, `chunk_id`, `title`, `snippet`) used for authorization and publication filtering.
- Hybrid retrieval tests must cover dense-only, sparse-only, fused, filtered, empty, duplicate, and rank-fusion cases. Qdrant's server-side RRF and the application's Evidence Fusion stage are separate contracts.
- The `ObjectStorage` port and MinIO adapter are retained for future document/artifact storage needs, but v1 Compose no longer provisions object storage; dev/test object use a local filesystem adapter behind the same port (ADR 0017 update).
- Official references: [Qdrant Hybrid Query](https://qdrant.tech/documentation/concepts/hybrid-queries/), [Qdrant RRF](https://qdrant.tech/documentation/concepts/hybrid-queries/#fusion), [fastembed SparseTextEmbedding](https://qdrant.github.io/fastembed/examples/Sparse_Text_Embedding/), [Qdrant sparse vectors](https://qdrant.tech/documentation/concepts/vectors/#sparse-vectors).
